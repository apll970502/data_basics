## 3-4. JOIN 상세 결과 관찰

```text
학생 A가 나타난 행 수: 2행
학생 B가 나타난 행 수: 1행
학생 C가 나타난 행 수: 없음
```

다음 질문에 답합니다.

### Q1. 학생 C가 왜 결과에서 사라졌나요?

```text
질문을 안썼기 때문에/ 알아보니깐 INNER JOIN에서 통째로 빠졌다한다
INNER JOIN은 두테이블에 모두 매칭되는 데이터만 보여준다고한다.
학생 C는 질문 테이블에 매칭 되는 행이 없어서 결과에서 제외된것이다
```

### Q2. 학생 A가 왜 여러 행으로 나타났나요?

```text
학생 A는 두번 나타남 - 질문을 2개 썼기 때문에 행이 2개로 늘어난다..
```

### Q3. 위 `COUNT(*)`가 실제로 세고 있었던 것은 무엇인가요?

```text
COUNT(*) = 3은 학생수가 아니라 학생 질문 매칭행의 개수를 센것 우연히 학생 수랑 똑같이 나온것이다
``` 

### Q4. 결과 숫자가 우연히 실제 학생 수와 같아도 바로 믿으면 안 되는 이유는 무엇인가요?
```text
숫자가 원하는 답과 같아도 그숫자가 무엇을 세고 있었는지 확인 하지 않으면 실제로는 완전히 다른걸 세고 있었을 수 있다. 데이터가 조금만 바뀌어도 숫자가 4로 바뀌면서 진짜 학생수와 달라지게 된다고한다
```

## 3-5. 질문 한 건을 추가한 뒤 다시 실행

추가한 데이터:

```text
INSERT INTO ch01_questions (question_id, student_id, question_text)
VALUES (104, 1, '네 번째 질문');
```

다시 실행한 결과:

```text
AI SQL 결과: 4
실제 학생 수: 3
```

### 결과 해석

```text
데이터가 바뀐 뒤 무엇이 달라졌는지: 질문만 더한건데 학생수가 달라졌어요

실제 학생 수는 왜 그대로인지: 그냥 A가 질문을 1개 더했을뿐이기에

이 실험을 통해 알게 된 점: 실제 학생수는 전혀 안바뀌었는데 전채학생수를 질문갯수가 바꿔버리는 오류발생
이를 해결하려면은
- INNER JOIN 방식: 학생과 질문이 매칭된 "행"의 개수를 센다 (질문 개수에 영향받음)
- 단순 COUNT(*) FROM ch01_students: 순수하게 학생 테이블의 행(=학생) 개수만 센다
이렇게 하면된다
```

# 4. 잘못된 데이터가 결과를 바꾸는 과정

## 4-1. 주문 데이터 확인

다음 데이터를 입력한 뒤 실제 결과를 확인합니다.

```text
ORD-001, 100000
ORD-002, 200000
ORD-002, 200000
```

## 4-2. 실행 전 예상

업무적으로 주문이 `ORD-001`, `ORD-002` 두 건이고 `order_code`가 주문을 고유하게 구분한다고 **가정할 경우** 예상 합계:

```text
300,000원
```

> 위 가정 자체가 실제 업무 규칙인지 확인해야 한다는 점도 기억합니다.

## 4-3. SQL 합계

```sql
SELECT SUM(amount) AS total_amount
FROM ch01_orders;
```

실제 결과:

```text
500000 원
```

## 4-4. 결과 해석

### `SUM` 문법 자체가 잘못된 것인가요?

```text
아닙니다 sum 문법은 제대로 썼으나 테이블에 저장되어있는 3개를 정확하게 더한것이고 sql 자체는 문제 없이 작동했다
```

### 결과 차이의 원인은 무엇인가요?

```text
데이터 자체에 문제가 있다 ord-002라는 같은 주문 코드가 두번 입력 되어있었고 , 서로 다른 두건의 주문으로 인식해서 그대로 더하게 되었다
```

### SQL이 정확하게 실행되어도 업무 숫자가 잘못될 수 있는 이유를 설명하세요.

```text
SQL은 저장된 데이터를 있는 그대로 계산한거고 이게 적절하게 들어갔는지 틀린지 판단하면 안된다 데이터 입력 과정에서 중복이나 오류가 아무리 SQL문법이 정확해도 결과는 의도와 다르게 잘못 작동된다 따라서 SQL 실행이 된다고 그게 의도한바 값이 나온다는 것은아니다

```

## 4-5. AI에게 같은 데이터를 분석시킨 결과

AI가 계산한 합계:

```text
총 500,000원 
```

AI가 중복 가능성을 언급했나요?

```text
네 언급했습니다 주문 코드가 두번 등장하는것을 언급 이게 실제 두개의 별도 주문인지 아니면 같은 주문이 잘못 중복 입력된지 확인이 필요하다 얘기했다.
```

AI가 `ORD-002` 두 행이 실제 두 주문인지 중복 입력인지 스스로 확정할 수 있나요? 이유도 적으세요.

```text
확정할수 없다 ai는 적힌 값만 볼수있을뿐 그값이 실제 업무에서 왜 두번생겼는지 같은 상품이 두번입력된건지 실수로 두번적힌건지 진짜 두개인건지 데이터만 봐서는 확인이 어렵다
```

추가로 확인해야 할 업무 규칙:

```text
1. order_code가 주문을 고유하게 식별하는 값인지 아니면 같은 상품코드로 된 상품을 여러 번 주문할수있는지
2. 같은 order_code가 두번 나오면 이걸 정상으로 볼지 데이터 오류로 볼지 정한 규칙이 있는지
3. 실제 원본 데이터를 대조해서 이줌누이 진짜 두건인지 확인할 방법이 있는지
```

내가 최종적으로 내린 판단:

```text
현재 데이터만으로는 이게 정상적인 두건의 주문인지 중복 입력 오류인지 판단할 수 없다고 결론지었다. AI의 계산 자체는 SUM함수가 제대로 들어갔지만 그숫자가 적절하게 들어갔는지 보려면 먼저 데이터 원본을 확인하는 절차를 거치는것이 좀더 명확하다
```

# 5. 파일·스프레드시트·DBMS 선택 연습

각 사례에 대해 **AI에게 묻기 전에 먼저 본인의 판단을 작성**합니다.

## 사례 A. 개인 독서 기록

```text
나의 선택:  파일 또는 간단한 스프레드시트
선택 이유: 혼자쓰고 데이터 양이 적기에 동시 수정하는 복잡한관계가 없어서 DBMS까지 쓸 필요가 없다. 가볍게 기록하고 훑어보는 용도로 충분
어떤 조건이 추가되면 다른 방식으로 바꿀 것인지: 여러사람과 독서기록을 공유하거나 책과 저자 장르같은 관계를 복잡하게 분석해야 하면 DBMS가 필요할수있다생각한다.
```

## 사례 B. 동아리 행사 신청 명단

```text
나의 선택: 스프레드시트(구글)
선택 이유: 여러명이 동시에 수정해야 하고 참석률 계산같은 집계가 있지만 간단하기에 DBMS를 굳이 안써도 되고, 구글시트는 동시 편집과 간단한 함수계산을 지원합니다.
어떤 조건이 추가되면 다른 방식으로 바꿀 것인지: 행사가 매번 반복되고 참가자이력을 계속 누적 관리해야하거나, 권한을 부여해야한다면 DBMS로 옮기는편이 나을수있다.
```

## 사례 C. 온라인 강의 서비스

```text 관계형 DBMS
나의 선택: 관계형DBMS
선택 이유: 학생-강의 다대다 관계, 신청 상태 변경, 금액 이력 보존, 동시 다수 사용자, 권한과 복구까지 요구되기 떄문에 파일이나 스프레드시트로는 안정적으로 처리하기 어렵습니다. 트랜잭션과 데이터 무결성이 중요한 서비스이기떄문입니다
```
